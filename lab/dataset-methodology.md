# Методика сбора лабораторного набора данных

Цель методики — получить воспроизводимый набор сетевых событий, где каждое событие можно связать с известным сценарием, временным окном, источником, целью и ожидаемой меткой.

## Принципы

1. Все прогоны выполняются только в изолированной лабораторной сети.
2. Внешние адреса запрещены.
3. Каждый сценарий описывается манифестом YAML.
4. Для сценариев задаются длительность, интенсивность, перечень разрешённых целей и ограничения безопасности.
5. Сырые логи и PCAP не хранятся в Git.
6. Разметка строится по временным окнам сценариев и сохраняется отдельно от сырых событий.

## Зачем нужен обычный фоновый трафик

Модель обнаружения инцидентов не должна учиться только на искусственно выделенных атаках. В реальной сети подозрительная активность смешана с обычными действиями пользователей и сервисов. Поэтому набор данных должен включать запросы HTTP, активность DNS, обращения к API, административные подключения и скачивание небольших файлов.

Фоновый трафик нужен для оценки ложных срабатываний. Без него модель может показывать завышенное качество в тестах, но плохо работать на обычной активности.

## Почему сценарии атак вплетаются в обычную активность

Контролируемые сценарии атак запускаются на фоне безопасной активности, чтобы приблизить набор данных к реальному потоку событий. Это помогает проверять:

- устойчивость признаков;
- качество временной разметки;
- смешение классов;
- влияние шума на уверенность модели;
- долю ложных срабатываний и пропусков атак.

## Формирование датасета

1. Подготовить план прогона.
2. Запустить обычный фоновый трафик.
3. Выполнить контролируемые сценарии по расписанию.
4. Собрать логи Zeek и Suricata.
5. Нормализовать события в JSONL.
6. Сформировать манифест временных окон.
7. Объединить события с метками.
8. Построить агрегированные признаки.
9. Создать отчёт о наборе данных.

## Ограничения v0.1

Стенд Docker v0.1 является прототипом. Он не моделирует полностью поведение корпоративной сети и не заменяет отдельный стенд на виртуальных машинах. Полученный набор данных должен рассматриваться как лабораторный материал для отладки конвейера, а не как окончательный набор для промышленной оценки.

## Выполнение и нормализация

После создания манифеста сценарии можно выполнить по нему. В v0.1 поддерживаются два режима:

- обычное выполнение внутри сети Docker с обращениями только к `target-web`, `target-api` и `control-api`;
- режим имитации, который не выполняет сетевые обращения, но записывает служебные события выполнения и синтетические учебные события трафика.

Результат выполнения сохраняется в двух уровнях:

- `execution_events.jsonl` - служебный журнал выполнения сценариев;
- `traffic_events.jsonl` - учебные события сетевой активности внутри сценариев.

Затем оба файла нормализуются в `lab/output/normalized_events.jsonl`, после чего формируется `dataset_report.md`.

Режим имитации формирует синтетические лабораторные события и нужен для проверки конвейера. Для обучения итоговых моделей требуется реальный сбор трафика в Docker или стенде VMware и последующая проверка качества набора данных.

## Построение признаков

Сырые события не являются готовыми признаками для модели. Для обучения используются наборы данных, агрегированные по временным окнам и сетевым потокам:

```text
raw events -> normalized events -> feature extraction -> windows.csv / flows.csv -> training
```

Набор по временным окнам строится по периодам наблюдения. Набор по сетевым потокам v0.1 группирует события по роли источника, роли цели, сценарию и типу события. После подключения Zeek и Suricata потоковое представление должно быть расширено реальными сетевыми полями.

`scenario_id`, `run_sequence` и плановое время используются только для разметки и анализа, но не являются входными признаками модели. Эти поля сохраняются как метаданные и должны исключаться перед обучением.

## Филин v0.2: происхождение событий

В режиме Docker `traffic_events.jsonl` фиксирует результаты реальных безопасных действий между контейнерами. Поля `execution_mode`, `synthetic` и `observation_source` описывают происхождение записи и исключаются из признаков модели, чтобы модель не получила прямую подсказку о режиме формирования данных. Эти записи являются наблюдениями клиента, а не полным захватом сетевого трафика.
