# Архитектура контролируемой локальной репетиции v0.3.17

Архитектура предназначена только для технической локальной репетиции на новых синтетических данных. Она не является реальным пассивным наблюдением, серверной частью, SIEM, системой промышленной эксплуатации или внешней проверкой.

## Компоненты и границы доверия

`traffic-source` создаёт новые секундные сегменты PCAP с заданным числом независимых синтетических окон. Оркестрация на узле закрывает сегмент до обработки, строит 51 причинно допустимый признак по неизменному контракту `network_features_v2`, однократно применяет зафиксированного кандидата к каждому окну и передаёт проверенное по схеме событие `shadow_event_v2` в дополняемый входной поток датчика.

`sensor-runtime` читает только завершённые записи JSONL, хранит контрольную точку со смещением в байтах на выделенном томе и передаёт пакеты до 50 событий через TLS 1.3/mTLS. Контрольная точка обновляется только после долговечного подтверждения ACK от соединительного модуля.

`staging-connector` проверяет неизменные контракты входящих данных и событий, выполняет фиксацию SQLite WAL в режиме `FULL` до ACK и доставляет пакеты в `reference-receiver`. Ограниченная очередь содержит до 200 пакетов; долговечный обработчик ожидающих записей восстанавливает незавершённые записи после перезапуска и исключает повторное получение прогноза.

В итоговой редакции протокола 5 обе границы mTLS/TLS 1.3 повторно используют последовательные соединения HTTP/1.1 с переподключением после ошибки. Насос ожидающих событий обращается к долговечному журналу через индекс `(delivery_status, journal_durable_ns, event_id)`. Очищенные трассировки наблюдаемости соединительного модуля и приёмника записываются в отдельные локальные файлы SQLite WAL; они не участвуют в контрактной фиксации или подтверждении ACK. Основные журнал, контрольная точка и хранилище приёмника сохраняют прежние схемы и режим долговечности `FULL`. Перед автономным снимком выполняется явная контрольная точка WAL всех четырёх локальных баз.

Итоговая редакция 6 закрепляет физическую независимость запусков: общий каталог кампании содержит только дополняемый входной поток, управляющие данные и сертификаты, а каждый запуск монтирует собственный каталог `<run_id>/volumes` для контрольной точки датчика, журнала соединительного модуля и хранилища приёмника. После завершения запуска его тома больше не подключаются к последующим запускам; автономные снимки остаются внутри корня соответствующего запуска.

`reference-receiver` проверяет неизменяемый контракт пакета и реестр обязательств, выполняет долговечную транзакцию SQLite, обеспечивает идемпотентность и возвращает ACK только после фиксации.

`operator-view` подключает том приёмника только для чтения, открывает SQLite через `mode=ro`, публикует только `operator_projection_v1`, поддерживает `GET` и `HEAD` и возвращает `405 read_only` для любых методов записи. Изменяемая база данных, права записи приёмника и элементы управления действиями отсутствуют.

## Сети

Используются ровно три сети Docker с `internal: true`:

- `filin_sensor_connector_internal`: источник трафика, среда выполнения датчика и промежуточный соединительный модуль;
- `filin_connector_receiver_internal`: промежуточный соединительный модуль и эталонный приёмник;
- `filin_receiver_operator_internal`: эталонный приёмник и операторское представление.

Опубликованные порты, сеть узла, внешние маршруты, внешняя DNS и маршрут к серверной части отсутствуют. Представление оператора не имеет пути к датчику или соединительному модулю.

## Усиление защиты и хранилища

Все контейнеры запускаются как UID/GID `65532`, с корневой файловой системой только для чтения, `no-new-privileges`, `cap_drop: ALL`, без привилегированного режима, сокета Docker и файловой системы узла. Области для записи ограничены отдельными привязками и томами среды выполнения и `/tmp` tmpfs. Каждый компонент имеет ограничения памяти, CPU и числа процессов, зафиксированное значение `restart: no` и проверку здоровья. Синтетические закрытые ключи находятся только в игнорируемой Git среде выполнения и имеют требуемый режим `0600` на поддерживающей его файловой системе.

Исходные PCAP, признаки, прогнозы, события, журналы, базы данных, снимки, сведения о ресурсах и трассировки задержек не входят в Git. В комплект подтверждающих материалов допускаются только очищенные агрегаты, манифесты, контрольные суммы и причинно связанные отчёты.
## Уточнение границы запусков в редакции 7

До запуска нового контейнера источника оркестратор удаляет общий устаревший
`control.json` и маркер предыдущего завершения. Новая управляющая запись становится видимой
только после готовности нового стека с отдельным `<run_id>/volumes`. Это не даёт
источнику повторно выполнить расписание предыдущего запуска на переходной границе.
## Долговечное хранилище и обслуживание в редакции 8

Датчик, соединительный модуль и приёмник каждого запуска используют отдельные именованные тома Docker.
Они не переиспользуются между запусками. После сверки
оркестратор создаёт контрольную точку WAL и копирует основные базы данных и базы трассировок в
`<run_id>/offline_storage`, после чего следующий запуск получает новые тома.

Файлы синтетических сертификатов заменяются через временный файл и атомарное переименование.
Перезапуск выполняется как ограниченная остановка `stop`, затем подъём `up --no-deps`, после чего
оркестратор ждёт рабочего и исправного состояния всех затронутых компонентов.
