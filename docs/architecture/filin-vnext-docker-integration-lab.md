# Интеграционная Docker-лаборатория Filin `vNext`

## Назначение и доказательная граница

`lab/vnext` — одноразовая инженерная среда. Она подтверждает прохождение
настоящего трафика через контейнерную сеть, `tcpdump`, Zeek, существующий
синтаксический анализатор, нормализацию, вычисление признаков и два базовых
детектора. Среда не является научной кампанией, не создаёт набор данных, не
обучает модель и не меняет исторические версии v1–v5.

Проект разделяет четыре уровня проверки:

1. модульные тесты проверяют функции и контракты на данных Python;
2. быстрые проверки исполняют генераторы через встроенный сервер обратной петли, но не создают PCAP и журналы Zeek;
3. интеграционные Docker-проверки создают настоящий сетевой обмен и проверяют всю техническую цепочку;
4. научная кампания требует отдельного зафиксированного протокола, независимых данных и статистического анализа; лаборатория таких выводов не делает.

## Аудит существующих быстрых проверок

После добавления обычной навигации текущий реестр содержит 24 определения:
22 исполняемых и 2 запланированных. Упоминание 21 сценария относится к более
раннему состоянию реестра. Все 22 исполняемых определения используют один
`run_smoke`: настоящий сетевой ввод-вывод через обратную петлю к
`ThreadingHTTPServer` внутри того же процесса Python. Захват пакетов и Zeek
отсутствуют. Файл `raw/activity.jsonl` формируется из клиентских записей
генератора. Затем локальный нормализатор строит `network.flow` из записей
соединений и HTTP, `http.request` — из записей ответов HTTP, а `auth.attempt` —
из клиентской интерпретации кода ответа. Встроенный сервер является настоящей
локальной целью, но не независимым сервисом. В `run_smoke` нет имитаций;
модульные тесты контрактов используют фикстуры Python и не являются

## Топология и безопасность

```text
generator ── TCP/HTTP ──► target-http / target-auth
    │ общее сетевое пространство имён
    ▼
 sensor (tcpdump) ──► PCAP ──► zeek ──► conn.log/http.log
                                           │
 target-auth JSONL ─────────────────────────┤
                                           ▼
 анализ → события → наблюдение → признаки → обнаружение
```

Compose создаёт внутреннюю мостовую сеть `filin-vnext-lab` без опубликованных
портов и без сети узла. Настройка `internal: true` закрывает обычный внешний
исходящий доступ. Среда исполнения принимает только имена `target-http` и
`target-auth`, точный список разрешённых портов и окружение
`vnext-docker-lab`. Параметра произвольного назначения в командной строке нет.
Ограничены число запросов, длительность, параллелизм, процессор, память и число
процессов. Привилегированный режим не применяется. Только сенсор получает
`NET_RAW` и `NET_ADMIN`, необходимые для захвата, и разделяет сетевое
пространство имён генератора. Пароли представлены детерминированными вымышленными
строками стенда; секреты не записываются в телеметрию цели.

## Контейнеры, образы и жизненный цикл

Во время `up` и `run` в Docker Desktop видны:

- `filin-vnext-target-http` и `filin-vnext-target-auth`;
- `filin-vnext-generator`;
- `filin-vnext-sensor`;
- `filin-vnext-zeek`.

Используются только образы разработки `filin-vnext-dev/target`,
`filin-vnext-dev/generator`, `filin-vnext-dev/sensor` и
`filin-vnext-dev/zeek`. Метки OCI содержат исходный коммит, отдельное время
сборки, SHA-256 файла `Dockerfile`, контрольную сумму выбранного контекста сборки
и инженерную классификацию. Это происхождение среды разработки, а не научная
фиксация образов.

Команды из корня репозитория:

```powershell
python -m lab.vnext.labctl up
python -m lab.vnext.labctl run
python -m lab.vnext.labctl inspect
python -m lab.vnext.labctl down
```

`run` намеренно оставляет контейнеры работающими для визуальной проверки;
`down` удаляет контейнеры и сеть. PCAP и производные сохраняются только в
`.filin-engineering/vnext/docker-runs/`. Вложенный файл `.gitignore` исключает
содержимое этого инженерного каталога из Git, не меняя защищённый корневой файл.

## Интеграционная матрица и артефакты

Матрица содержит 11 запусков: обычную навигацию, проверку работоспособности,
опрос API, ошибочную настройку аутентификации, последовательную и случайную
разведку, перебор путей, полный перебор реквизитов, распыление паролей,
периодическое и неравномерное сигнальное обращение. Для разведки, злоупотребления
реквизитами и сигнальных обращений используются независимые реализации A/B.
Инженерное сравнение сопоставляет число пакетов и соединений, интервалы,
распределение целей и последовательность запросов только для подтверждения
различия сетевых трасс; это не научные показатели.

Каждый каталог запуска содержит настоящий `capture/traffic.pcap`, журналы Zeek,
JSONL цели аутентификации при необходимости, нормализованные события, пакет
наблюдений, пакет признаков, результат обнаружения, пакет объяснения, диагностику
и манифест. Манифест связывает реализацию, идентификаторы образов, сеть,
возможности цели, времена, SHA-256 PCAP и журналов, а также контрольные суммы
всех последующих пакетов. Истинная разметка остаётся вне пути предсказания.

Интеграционная проверка запускается явно:

```powershell
$env:FILIN_RUN_DOCKER_INTEGRATION = '1'
python -m pytest -m docker_integration ml/tests/test_vnext_docker_integration.py
```

Без явного включения обычный запуск тестов получает понятный пропуск. Если
включение задано, но служба Docker недоступна, тест также получает пропуск с
причиной, а не фиктивный успешный результат.
