# Руководство по эталонному приёмнику

Эталонный приёмник — локальный изолированный компонент для проверки доставки `shadow_event_v2`. Он не является серверной интеграцией, SIEM или каналом автоматического ответа.

## Перед запуском

Проверьте реестр кандидатов, схему события, контрольную сумму конфигурации и адрес `127.0.0.1`. Приёмник использует взаимную проверку сертификатов TLS, а не одноразовый токен консоли. Перед проверкой зафиксируйте версию кода и убедитесь, что тестовый поток не содержит реальных секретов или внешних адресатов.

Источники процедуры — `staging/reference_receiver/app.py`, `staging/http_runtime.py` и `staging/storage.py`. Параметры запуска:

| Параметр | Назначение |
|---|---|
| `--host` | Для ручной локальной проверки явно задать `127.0.0.1`; значение парсера по умолчанию — `0.0.0.0` |
| `--port` | Порт HTTPS, по умолчанию `9443` |
| `--db` | Путь к базе SQLite; для локальной проверки выбрать отдельный файл в `runtime/` |
| `TLS_CERT` | Переменная окружения с путём к сертификату сервера |
| `TLS_KEY` | Переменная окружения с путём к закрытому ключу сервера |
| `TLS_CLIENT_CA` | Переменная окружения с путём к доверенному центру сертификации клиентов |
| `RECEIVER_INSTANCE_ID` | Необязательная идентичность экземпляра |

Безопасно посмотреть параметры: `python -m staging.reference_receiver.app --help`. Перед настоящим запуском сертификаты и пути должны быть подготовлены оператором; ключи не публикуются в репозитории. После этого запускается модуль `staging.reference_receiver.app` с явно выбранными адресом и базой. Запуск создаёт постоянное состояние в SQLite.

## Граница ответственности

Приёмник проверяет локальную доставку пассивного события и не является частью научной Phase 1. Он не получает данные сопоставления, метки или сырые материалы сетевой проверки. Его успешный ответ не доказывает качество модели, готовность промышленной интеграции или внешнюю валидность.

## Приём и проверка

Конечная точка — `/reference-receiver/v1/event-batches`. Приёмник проверяет пакет через `validate_batch`, сохраняет его через `ReceiverStore.commit` и возвращает квитанцию. Повторная доставка проверяется по ключам идемпотентности в контракте хранилища. Событие сохраняется как пассивное наблюдение; оно не вызывает уведомление, блокировку или изменение кандидата. После каждого набора запросов сверяйте число принятых и отклонённых событий с локальным отчётом.

## Разбор отказа

Сохраните код завершения, первое сообщение, входной идентификатор и контрольную сумму. Проверьте схему, сертификаты TLS, адрес и доступность базы. После локального исправления повторите узкую проверку транспорта. Если причина не воспроизводится, не объявляйте транспортный результат подтверждённым.

## Очистка и результат

После проверки остановите локальный процесс, удалите только временные материалы теста и убедитесь, что внешний адрес не был опубликован. Зафиксируйте версию схемы, число входов, число принятых событий и контрольные суммы локального отчёта. Не помещайте токены и полезные нагрузки в документацию или репозиторий.

## Граница доказательства

Успешная доставка подтверждает только локальный transport trial. Она не подтверждает внешнюю валидность модели и не разрешает промышленную эксплуатацию. Связанные правила: [модель безопасности](../safety-model.md), [текущий статус](../status/current-status.md) и [команды](../reference/command-reference.md).
